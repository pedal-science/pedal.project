# Rig schemas

JSON Schema (Draft 2020-12) models of the two ways a rig exists on its way to the pedal:

| File | Models |
|---|---|
| [`ljoss-rig.schema.json`](ljoss-rig.schema.json) | The **designer's** rig document — what ljoss saves on disk (one file per rig, `<uuid>.rig.json`). A series/parallel *tree*. |
| [`namchain-rig-document.schema.json`](namchain-rig-document.schema.json) | The **engine's** rig document — what `rig.apply` accepts, `rig.get` returns, and the daemon keeps as `last.json`. A flat *graph* of nodes and connections. This is the version a rig is transformed into before running on namchain. |
| [`namchain-engine-schema.schema.json`](namchain-engine-schema.schema.json) | The engine's own node catalogue (the `engine.schema` answer): every node type and macro with its parameters, so the names the document schema allows can be checked against what the engine declares. |
| [`examples/`](examples/) | One valid document for each schema. The ljoss example and the namchain example are the **same rig** before and after the transformation. |
| [`schema-graph.drawio`](schema-graph.drawio) | Both models (plus the catalogue and the transformation) as a layered graph — four pages, open in draw.io. |
| [`schema-graph.graphml`](schema-graph.graphml) | The same graph as GraphML for yEd. Generated by [`tools/schema-graph.py`](../../tools/schema-graph.py); [`preview/`](preview/) holds PNG renders of each page. |

## One rig, two shapes

ljoss owns the tree and its editing model; namchain owns the graph and its parser. The two
checkouts on the Mac sit side by side (`~/code.local/ljoss`, `~/code.local/namchain`), and the
split of work is fixed: **ljoss flattens the topology, the engine lowers the blocks.**

```
ljoss Rig (tree)                              namchain rig document (graph)
─────────────────────────────  DocumentEncoder ────────────────────────────────
SignalChain input  ───────────────►  nc.input  ("in", element = input's UUID)
Block (enabled)   ───────────────►  1–2 nodes from BlockMapping
                                      • an amp  → nc.nam + fx.amp.tonestack
                                      • a cab   → fx.cab.ir
                                      • a delay → fx.delay.feedback
Block (disabled)  ───────────────►  same nodes, "bypass": true
ParallelSection (Y split) ───────►  nc.split (outputs = lanes)
                                    + one series per lane
                                    + nc.mix (inputs = lanes), lane i on port i
                                    (+ a nc.gain per lane carrying its
                                      level/mute/polarity as one linear gain)
SignalChain output level ─────────►  nc.gain (gain_db)
SignalChain output ───────────────►  nc.output ("out", element = output's UUID)
chain position    ───────────────►  input_channel / output_channel
```

The whole mapping is two small tables, kept closed on purpose so the two sides cannot disagree
about what a knob means:

- `ljoss/RigDesigner/Engine/DocumentEncoder.swift` — the flattening (tree → nodes, connections,
  refusals collected rather than thrown).
- `ljoss/RigDesigner/Engine/BlockMapping.swift` — which of the app's 102 catalogue blocks the
  engine can render (27 today), the transforms from catalogue values to engine parameters
  (0–10 knob → ±dB, % → 0–1, option names), the device assets a block needs (`engine.model`,
  `engine.ir`), and the parameters deliberately left out-of-band with a reason.
- `namchain/src/graph/rig.cpp` — the parser these schemas are transcribed from. It is the
  contract: it refuses unknown keys at every level except the node, where **any key that is not
  reserved is a parameter**.

Deliberate asymmetries, made explicit in the schemas rather than papered over:

- **Strictness.** The engine document is strict: an unknown key is a refused mistake (a client's
  own data goes in `meta`). The designer document is tolerant: Swift's Codable decoder ignores
  unknown keys so a rig saved by a newer build still loads.
- **Wrapping.** The designer document shows Swift's synthesized Codable shape — an enum with an
  associated value is `{"case": {"_0": …}}`, so a stored knob is
  `"gain": {"number": {"_0": 6.5}}` and a parallel section is `"parallel": {"_0": {…}}`. The
  engine document has no wrappers: a knob is just `"gain_db": -6`.
- **Trees vs graphs.** The tree can only say series/parallel, which is what the canvas draws;
  the graph says whatever nodes and connections say. What the tree *cannot* say (an A/B or
  crossover split, an unmapped block) is refused by name, not silently flattened.

## Where each model's source of truth lives

| Model | Source of truth |
|---|---|
| ljoss rig document | `ljoss/RigDesigner/Model/Rig.swift`, `CoreTypes.swift` (types); `Store/RigLibrary.swift` (encoding: `.sortedKeys`, `.prettyPrinted`, ISO-8601 dates) |
| namchain rig document | `namchain/src/graph/rig.cpp` (`parse_document_json`); also `namchain/docs/schema.md`, `docs/ui-integration-plan.md` §1 |
| engine node catalogue | `namchain/src/daemon/daemon.cpp` (`param_schema`, `node_type_schema`, `macro_type_schema`); types in `src/nodes/builtin.cpp`, `src/nodes/macros.cpp` |

These schemas were written against namchain `b9ca368` and ljoss `d9ad735`; the code is the
contract and the schemas are a transcription, so re-check them when either repo changes its
format. Per "one home per fact" (`docs/working-across-repos.md`), the long-term homes are the
owning repos — the namchain document schema beside `src/graph/rig.cpp`, the ljoss one beside
`Model/Rig.swift` — and this directory can be replaced by links once they land there.

## Exploring the models as a graph

[`schema-graph.drawio`](schema-graph.drawio) is the same content as the schemas, drawn as
vertices and edges so it can be explored rather than read. Four pages in one file:

1. **ljoss rig tree** — every object type in the designer's document, the containment edges
   with their cardinalities, the unions (`ChainElement`, `ParamValue`) and the enums, and the
   dashed edge to the catalogue where defaults actually live.
2. **namchain rig document** — the engine document: the two accepted forms (chains / legacy),
   nodes and connections, and the `type → NodeType` reference into the catalogue.
3. **engine.schema catalogue** — the palette entities: `NodeType`, `MacroType`, `Param`,
   `Role`, `Target`, the enums, and the two lists of actual types (11 primitives, 7 macros).
4. **tree → document → lowered graph** — the transformation itself, left to right: ljoss
   blocks on the left, the document nodes they flatten into in the middle, and the primitives
   the engine lowers each macro to on the right — including `fx.amp.tonestack`'s three
   biquads, `fx.cab.ir`'s four nodes, and `fx.delay.feedback`'s feedback loop with the
   `nc.unit_delay` that keeps it a DAG. Red edges are the refusals.

Open it in **draw.io** (desktop app or diagrams.net): drag vertices, pan/zoom, use the search
box to find e.g. "Target", collapse the pages panel, or open the *Edit → Edit data* table for
a flat list. The same graph is also in [`schema-graph.graphml`](schema-graph.graphml), which
**yEd** (free) imports — it is the better explorer: `Tools → Fit Node to Label`, then
`Layout → Hierarchical`, and its neighbourhood view and filtering make the four tabs easy to
wander. PNG renders of each page are in [`preview/`](preview/) for a quick look without
opening either tool.

Both files are generated from [`tools/schema-graph.py`](../../tools/schema-graph.py), which
holds the graph data next to the layout code, so the diagram and the schemas are edited in
one place and re-emitted:

```sh
python3 tools/schema-graph.py                          # rewrite .drawio and .graphml
```

## Loading into a schema designer

These are plain JSON Schema 2020-12, which every mainstream schema tool reads:

- **Stoplight Studio** (free, desktop, macOS) — the closest thing to a dedicated schema
  designer: *File → New → JSON Schema → Import* one of the `.schema.json` files and it opens as
  an editable visual tree, with the examples usable as test fixtures.
- **VS Code** — the Red Hat YAML extension validates `.json`/`.yaml` against a `$schema`. Open
  any of the three schemas as a workspace document; open `examples/*.json` alongside and edit
  with live validation. (The namchain example carries no `$schema` hint on purpose: the engine
  refuses unknown keys, and `$schema` would be one.)
- **Hackolade Studio** (commercial) — the heavyweight JSON schema design tool; imports these
  directly for polyglot data modelling.
- **Postman / Insomnia** — import a schema under APIs/Schemas to get validation while testing
  the daemon's protocol by hand.

All three schemas validate against the 2020-12 meta-schema, and a throwaway checker in
`build/schema-check/` (gitignored) proves the examples **and** namchain's real committed rigs
(`rigs/guitar-chain.json` legacy form, `rigs/two-chains.json`, `rigs/four-chains.json`) against
them, plus sixteen negative cases that mirror the parser's refusals:

```sh
cd build/schema-check && npm i ajv ajv-formats && node check.mjs   # ALL CHECKS PASSED
```

If a designer complains about a construct, the non-obvious one is in the document schema's node
definition: `patternProperties` with a negative lookahead
(`^(?!(?:id|type|element|role|params|strings|bypass|meta)$)`) is how the "every other key is a
parameter" rule is expressed — that is the engine's own rule, not schema sugar.
