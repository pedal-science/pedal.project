The pedal's Core host vip is a Raspberry Pi 5 with a SparkFun WM8960 codec as I2S master, set up through a simple-audio-card overlay and a mixer state file applied at boot by pedal-codec. `docs/hardware-handoff.md` (D8) says the class-D speaker amp is a switching noise source next to the ADC inputs and must be unpowered; SPKVDD on the stock board is currently bridged to VIN, so the amp has power. This came up while debugging a right-channel output problem; the software path itself was confirmed fully stereo and is not the subject of this task.

Task:
On vip (the Core host), the WM8960's class-D speaker amplifier is powered and enabled, though the design says it must stay off. Read on 2026-10-16 with namchaind running: R26 (0x1a, Power Mgmt 2) = 0x01f9, so the SPKL and SPKR power bits (4 and 3) are set; R49 (0x31, Class D Control 1) = 0x00f7, so SPK_OP_EN = 11 (both outputs on). The 'Speaker Playback Volume' control is 0 (muted). The overlay `pedal.project/devices/common/rootfs/etc/pedal/codec/wm8960-codec-master.dts` assumes that leaving out a speaker widget keeps DAPM from powering the amplifier. Apparently it doesn't: the codec's unconnected SPK_LP/LN/RP/RN outputs are probably still DAPM endpoints, because the card isn't fully routed.

Task: find out why DAPM powers the speaker path, then fix it so it stays down from boot. Candidate fixes: route the speaker outputs to a widget that's never enabled, mark the pins not-connected, or use simple-audio-card pin switches applied by `pedal-codec`. Pick the cleanest one, in the overlay or the boot-time codec setup in `pedal.project`. Update `wm8960.mixer`'s comment and `devices/<host>/check`, if it should assert this. Done means R26 bits 4:3 and R49 bits 7:6 read 0 on vip while audio plays, and both headphone outputs still work. Read `pedal.project/AGENTS.md` first.
